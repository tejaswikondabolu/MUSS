# Hogwarts School of Witchcraft & Programming

A multi-agent AI system themed as a satirical Hogwarts programming museum. Users ask programming questions and receive answers from LLM-powered Hogwarts characters — Hermione (Rust), Snape (Python), Luna (C++), and Cedric (JavaScript) — each with distinct personalities, expertise, and language specialties.

**Tech stack:** Rust (Axum), Python (FastAPI + LangGraph), Ollama (gemma3:4b + nomic-embed-text), PostgreSQL, Qdrant

---

## 1. The Big Picture: What This Project Does

This is a **distributed multi-agent AI platform** disguised as a Harry Potter-themed web museum. It serves two purposes:

1. **Portfolio signal:** Demonstrates real AI engineering — multi-agent orchestration, RAG pipelines, vector databases, LLM integration, memory systems, and microservices architecture — all wrapped in a memorable theme.
2. **Educational toy:** Users can ask programming questions and see how different language experts (represented as Hogwarts characters) would answer, each from their own language's perspective.

The project started as a static Rust web app with hardcoded text responses and evolved into a full AI system where every character response is generated by a real LLM (gemma3:4b running locally via Ollama), orchestrated by a LangGraph state machine.

```

[1] Browser → GET /council/ask?question=What+is+ownership?
        │
        ▼

    │   Body: {"question": "What is ownership?", "user_id": "anonymous"}

        │
        ▼
[4] LangGraph Planner Graph (5 nodes)
    ├─ State: {question, user_id, context, history, responses (with concat reducer)}

    │   └─ PostgreSQL: get last 6 messages → history string
    ├─ Router node: returns [Send("hermione"), Send("snape"), ...] with context + history

    │   ├─ hermione: loads prompts/hermione.txt + context + history → calls Ollama
    │   ├─ snape:    loads prompts/snape.txt + context + history → calls Ollama

    └─ Reducer: concat_responses merges all partial state updates
        │
        ▼
[5] Ollama receives 4 requests (queued by Ollama's internal scheduler)
    ├─ Each request: {model: gemma3:4b, messages: [system_prompt, user_question]}
    ├─ Returns: {message: {content: "In-character response..."}}
    └─ Each response takes ~10-15 seconds on CPU
        │
        ▼
[6] Response flows back:
    Ollama → 4 agents → planner reducer → FastAPI → Rust → Browser
    Format:
    {
      "responses": [
        {"id": "rust", "name": "Hermione Granger", ..., "response": "..."},
        {"id": "python", "name": "Professor Severus Snape", ..., "response": "..."},
        {"id": "cpp", "name": "Luna Lovegood", ..., "response": "..."},
        {"id": "javascript", "name": "Cedric Diggory", ..., "response": "..."}

    }
        │
        ▼

[8] Browser displays 4 council member cards with their responses
```

### Fallback Mechanism

If the Python backend is unreachable (not started, crashed, or network issue):
- Rust catches the HTTP error or timeout
- Falls back to `council::get_debate()` — hardcoded string-matching responses from `council.rs`
- This ensures the site never breaks; users see deterministic answers if the AI backend is down

## 3. Phase 1: Single-Agent Foundation

### What was built

The initial AI integration replaced the hardcoded debate responses with a real LLM. A Python FastAPI backend was created alongside the existing Rust frontend, with a single agent — Hermione Granger — serving as the Rust programming expert.

### FastAPI Backend Structure

The Python backend exposes two endpoints:

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/health` | GET | Health check, returns `{"status": "🏰..."}` |
| `/council/ask` | POST | Accepts `{question, user_id}`, returns `{responses: [...]}` |

### Hermione Agent

The first agent was implemented as a standalone LangGraph StateGraph:

```python
# State: question + chat messages (with add_messages reducer)
class AgentState(TypedDict):
    messages: Annotated[Sequence[dict], add_messages]
    question: str

# Single node: loads system prompt, calls Ollama, returns AIMessage
async def hermione_node(state):
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": f"Question: {state['question']}..."},
    ]
    reply = await ollama_api(messages)
    return {"messages": [AIMessage(content=reply)]}

# Graph: start → hermione → end
builder = StateGraph(AgentState)
builder.add_node("hermione", hermione_node)
builder.add_edge("__start__", "hermione")
builder.add_edge("hermione", END)
```

### Ollama Integration

Ollama runs as a background service on `localhost:11434`. The model used is `gemma3:4b` — a 4.3 billion parameter model quantized to Q4_K_M (3.3 GB). It was chosen because:
- Runs on consumer hardware without a GPU
- Small enough for fast inference (~10-15s per response)
- Good enough quality for character-based responses
- Free and open-source

The agent constructs a prompt with a system message (Hermione's character definition) and a user message (the question), then sends it to Ollama's `/api/chat` endpoint.

### Rust Integration

The Rust `main.rs` was modified to:
1. Add `reqwest` HTTP client with JSON support
2. Define `FastAPICouncilResponse` and `FastAPIMemberResponse` deserialization structs
3. Update `council_ask()` handler to try the FastAPI backend first, fall back to hardcoded

The key insight is that the **response shape never changed** — the template expects `[{member: {id, name, ...}, response: "..."}]` whether the data comes from the LLM or from hardcoded strings.

## 4. Phase 2: Multi-Agent Council

### What was built

Phase 2 expanded from a single Hermione agent to all 4 Hogwarts characters, each as an independent LLM agent with its own personality, expertise, and language specialty. A LangGraph Planner orchestrates them using parallel fan-out.

### The Four Agents

| Agent | House | Language | Personality | Prompt Tone |
|-------|-------|----------|-------------|-------------|
| Hermione Granger | Gryffindor | Rust | Precise, condescending bookworm | References books, rules, "I've annotated it extensively" |
| Severus Snape | Slytherin | Python | Sarcastic, bitter professor | References potions, dungeons, thinly veiled contempt |
| Luna Lovegood | Ravenclaw | C++ | Dreamy, cryptic, eccentric | References Nargles, Wrackspurts, Crumple-Horned Snorkacks |
| Cedric Diggory | Hufflepuff | JavaScript | Warm, encouraging, humble | References Quidditch, Triwizard Tournament, fair play |

Each agent module exports:
- `MEMBER` dict — static metadata (id, name, title, icon, color, personality, expertise)
- `async def node(question: str) -> list[dict]` — calls Ollama with character prompt, returns response

### Architecture: LangGraph Planner with Send Fan-out

The core architectural pattern is a **LangGraph StateGraph** that uses the `Send` API for parallel execution:

```python
# Reducer: merges partial responses from parallel agents
def concat_responses(a: list | None, b: list | None) -> list:
    return (a or []) + (b or [])

# State: question + accumulated responses
class CouncilState(TypedDict):
    question: str
    responses: Annotated[list, concat_responses]  # reducer merges automatically

# Router: fans out to all 4 agents
def router(state: CouncilState) -> list[Send]:
    return [
        Send("hermione", {"question": state["question"]}),
        Send("snape", {"question": state["question"]}),
        Send("luna", {"question": state["question"]}),
        Send("cedric", {"question": state["question"]}),
    ]

# Each agent node calls its respective module
async def hermione_node(state):
    return {"responses": await hermione.node(state["question"])}
# ... same pattern for snape, luna, cedric

# Graph wiring
builder = StateGraph(CouncilState)
builder.add_node("hermione", hermione_node)
builder.add_node("snape", snape_node)
builder.add_node("luna", luna_node)
builder.add_node("cedric", cedric_node)
builder.add_conditional_edges("__start__", router, [...])
for name in ["hermione", "snape", "luna", "cedric"]:
    builder.add_edge(name, END)
```

### How Send Fan-out Works

`langgraph.types.Send(name, state)` is LangGraph's mechanism for dynamic parallel execution:
- The `router` function returns a list of `Send` objects, one per agent
- LangGraph creates a parallel task for each `Send`
- Each task receives a copy of the state and runs the named node
- When nodes complete, their return values are merged into the shared state using reducers
- All nodes must complete before the graph finishes

### Solving the Parallel Request Problem

A critical issue emerged: when 4 agents call Ollama simultaneously, each creates a new httpx connection. Ollama queues requests, but httpx's default timeout fires while waiting in the queue.

**Solution:** A shared httpx `AsyncClient` with connection pooling:

```python
_client: httpx.AsyncClient | None = None

def _get_client() -> httpx.AsyncClient:
    global _client
    if _client is None:
        _client = httpx.AsyncClient(
            timeout=httpx.Timeout(300.0, connect=10.0),
            limits=httpx.Limits(max_keepalive_connections=4, max_connections=4),
        )
    return _client
```

Benefits:
- Single TCP connection pool reused across all agents
- Keep-alive connections prevent port exhaustion
- 300-second read timeout accommodates Ollama's sequential queueing
- 4 max connections match the 4 concurrent agents

### Character Prompt Design

Each prompt follows a strict format to ensure consistent character behavior:

```
You are [CHARACTER NAME], [TITLE] at Hogwarts School of Witchcraft & Programming.

Your expertise: [LANGUAGE-SPECIFIC EXPERTISE]

Your personality: [CHARACTER TRAITS]

Your language specialty: [LANGUAGE]. You believe [LANGUAGE PHILOSOPHY].

Rules:
- Stay in character at ALL times. Never break character.
- Reference Hogwarts concepts in your explanations.
- [CHARACTER-SPECIFIC TONE INSTRUCTION]
- Keep responses to 2-4 paragraphs.
- Never mention you're an AI or a language model.
```

### The Rust Side: Zero Changes

Because Phase 1 already established the pattern of proxying through FastAPI, and the response shape (list of `{id, name, title, icon, color, personality, expertise, response}`) is identical regardless of how many agents respond, **no Rust code changes were needed** for Phase 2. The existing `FastAPICouncilResponse` struct and template code handle 4 responses as easily as 1.

## 5. Phase 3: RAG + Memory

### What was built

Phase 3 added a **Retrieval-Augmented Generation (RAG)** pipeline and **conversation memory** to the multi-agent council. Each agent now receives relevant documentation context (from Qdrant vector DB) and recent conversation history (from PostgreSQL) alongside the user's question, enabling more informed and context-aware responses.

### Infrastructure

Two Docker services were added alongside the existing Python backend:

| Service | Image | Port | Purpose |
|---------|-------|------|---------|
| **Qdrant** | `qdrant/qdrant:latest` | 6333 | Vector DB storing documentation chunk embeddings |
| **PostgreSQL** | `postgres:16` | 5432 | Persists sessions and message history |

Start them with:
```bash
cd ai-backend
docker compose up -d
```

### New Components

#### `db/qdrant.py` — Vector Search

Manages a Qdrant collection called `hogwarts_lore` with a 768-dimensional vector index (matching `nomic-embed-text`'s output size):

```python
async def ensure_collection():        # Creates collection if missing
async def search_context(query, top_k=3):  # Embed query → search Qdrant → return text chunks
async def upsert_docs(docs):          # Generate embeddings → upsert to Qdrant
```

Each document chunk stores:
- `text`: The documentation content
- `source`: Origin (e.g. "The Rust Book", "MDN")
- `language`: Programming language tag
- `character_id`: Which agent this is relevant for

#### `db/postgres.py` — Conversation Memory

Manages PostgreSQL connection pooling via asyncpg:

```python
async def init_pool():                # Create connection pool (min 1, max 4)
async def close_pool():               # Graceful shutdown
async def get_or_create_session(user_id):  # Get last session or create new one
async def save_message(session_id, role, content, agent_id):  # Persist message
async def get_history(user_id, limit=6):   # Get last N messages for user
```

Schema uses two tables:
- **sessions**: `(id UUID, user_id VARCHAR, created_at, updated_at)` — one per user conversation thread
- **messages**: `(id UUID, session_id FK, role VARCHAR, content TEXT, agent_id VARCHAR, created_at)` — individual turns

#### `agents/ollama.py` — Embedding Support

Added a `get_embedding(text)` function that calls Ollama's `/api/embeddings` endpoint with `nomic-embed-text` model. Returns a 768-dimensional float vector. This is used by both the Qdrant search and upsert pipelines.

#### `agents/memory.py` — LangGraph Memory Node

A new LangGraph node that runs **before** the agent fan-out:

```python
async def memory_node(state: dict) -> dict:
    # 1. Get embedding of question
    # 2. Search Qdrant for similar documentation chunks
    # 3. Format as context string
    # 4. Query PostgreSQL for recent conversation history
    # 5. Format as history string
    return {"context": "...", "history": "..."}
```

Both Qdrant and PostgreSQL calls are wrapped in try/except — if either service is unreachable, the node gracefully returns empty strings. The agents still work without RAG/memory infrastructure.

### Updated Architecture

The LangGraph graph now has 5 nodes instead of 4:

```
State: {question, user_id, context, history, responses}
         │
         ▼
    memory_node (NEW)
    ├─ Qdrant: search_context(question) → context
    └─ PostgreSQL: get_history(user_id) → history
         │
         ▼
    Router → Send fan-out to agents
    Each Send includes: {question, context, history}
         │
         ├──► hermione_node (prompt now includes context + history)
         ├──► snape_node
         ├──► luna_node
         └──► cedric_node
         │
         ▼
    concat_responses reducer → final response
```

### How Context is Injected into Agent Prompts

Each agent's `node()` function now accepts `context` and `history` parameters:

```python
async def node(question: str, context: str = "", history: str = "") -> list[dict]:
    system = SYSTEM_PROMPT
    if context:
        system += f"\n\nRelevant context from the archives:\n{context}"
    if history:
        system += f"\n\nRecent conversation history:\n{history}"
    # ... call Ollama with enriched system prompt
```

The context is appended to the **system prompt** (not the user message), so the character's personality and rules take precedence while the context provides factual grounding. This is a deliberate design choice — the character's voice should not be diluted by RAG content.

| Snape | "reference it with grudging acknowledgment... act as if you barely remember" |
| Luna | "accept it as if you already knew it... acknowledge it serenely" |
| Cedric | "incorporate it gratefully... reference it warmly" |

These rules maintain character consistency while enabling context-aware responses.

### Session Management in main.py

The FastAPI endpoint now tracks user sessions:

```python
@app.post("/council/ask")
async def council_ask(req: CouncilAskRequest):
    session_id = await get_or_create_session(req.user_id)
    if session_id:
        await save_message(session_id, "user", req.question)
    
    result = await council_graph.ainvoke({
        "question": req.question,
        "user_id": req.user_id,
        ...
    })
    
    if session_id:
        for r in result["responses"]:
            await save_message(session_id, "assistant", r["response"], r["id"])
```

Both the user's question and each agent's response are persisted, building up conversation history for future queries.

### Error Handling Philosophy

All database calls use graceful degradation:

| Scenario | Behavior |
|----------|----------|
| Qdrant unreachable | `search_context()` returns empty list → no RAG context |
| PostgreSQL unreachable | `get_history()` returns empty list → no conversation memory |
| Both unreachable | Memory node returns empty context + history → agents work from LLM knowledge only |
| Embedding model missing | `get_embedding()` raises → caught by caller → empty context |

This ensures the system never hard-fails due to missing infrastructure.

## 6. LangGraph Deep Dive

### Why LangGraph?

LangGraph was chosen over alternatives for these reasons:

| Alternative | Limitation | LangGraph Advantage |
|-------------|------------|---------------------|
| Direct async calls | Manual orchestration, no state management | Built-in state machine with reducers |
| LangChain chains | Sequential only, no branching | `Send` for dynamic parallel fan-out |
| Custom asyncio | No visualization, no checkpointing | Graph visualization, checkpoint/restore |
| CrewAI | Heavy abstraction, opinionated | Lightweight, flexible graph primitives |

### Key LangGraph Concepts Used

1. **StateGraph** — The base class for stateful graphs. State is a TypedDict with reducers.
2. **Reducers** — Functions that merge partial state updates. `concat_responses` appends lists.
3. **Nodes** — Async functions that receive state and return partial updates.
4. **Send** — Enables dynamic parallel execution. Nodes fan out and results merge via reducers.
5. **Conditional edges** — `add_conditional_edges` with a router function that returns `Send` objects.

### Graph Execution Flow

```
State: {question: "What is ownership?", responses: []}
         │
         ▼
    Router (conditional edge)
         │
         ├──► Send("hermione", state) ──► hermione_node ──► {responses: [r1]}
         ├──► Send("snape", state)    ──► snape_node    ──► {responses: [r2]}
         ├──► Send("luna", state)     ──► luna_node     ──► {responses: [r3]}
         └──► Send("cedric", state)   ──► cedric_node   ──► {responses: [r4]}
                                                  │
                                                  ▼
                                    concat_responses reducer:
                                    [] + [r1] + [r2] + [r3] + [r4] = [r1, r2, r3, r4]
                                                  │
                                                  ▼
                                    Final state: {question: "...", responses: [r1, r2, r3, r4]}
```

## 8. Key Technical Decisions

### Why Rust for the frontend?

- Performance and safety (ironic for a project about programming languages)
- Axum is a modern, fast async web framework
- Tera templates are familiar for Jinja2 users
- Demonstrates Rust web development skills alongside AI engineering

### Why Python for the AI backend?

- LangGraph is Python-only
- FastAPI has first-class async support and Pydantic validation
- Ollama's HTTP API is language-agnostic but Python has the best tooling
- Separation of concerns: Rust handles HTTP/routing, Python handles AI

### Why LangGraph instead of direct async calls?

- **State management:** LangGraph's reducer pattern cleanly handles merging parallel results
- **Extensibility:** Adding new agents is just adding a node and a Send entry
- **Visualization:** LangGraph can generate graph visualizations for documentation
- **Planned phases:** RAG, memory, and tool-calling all map to LangGraph patterns

### Why gemma3:4b instead of GPT-4 or Claude?

- **Zero API costs:** Runs entirely locally
- **Privacy:** No data leaves the machine
- **Offline capable:** No internet dependency
- **Sufficient quality:** For character-based responses, a 4B model is adequate
- **Trade-off:** Slower and less capable than GPT-4, but free and private

### Why Send fan-out instead of sequential calls?

- **Performance:** 4 parallel calls take ~15s total vs ~60s sequential
- **Independence:** Each agent's response doesn't depend on other agents
- **Scalability:** Adding more agents doesn't increase latency (up to Ollama's queue capacity)

### Why connection pooling for httpx?

- **Port exhaustion:** Without pooling, each agent creates a new TCP connection → 4 concurrent connections → potential port exhaustion
- **Timeout issues:** Default httpx timeout fires while waiting for Ollama to process queued requests
- **Performance:** Keep-alive connections eliminate TCP handshake overhead per request

## 9. Character Prompt Engineering

1. **Identity declaration:** "You are [character], [title] at Hogwarts..."
2. **Expertise listing:** Specific to the character and their language
3. **Personality traits:** 3-4 adjectives that define the character's voice
4. **Language philosophy:** What makes "their" language special
5. **Behavioral rules:** Stay in character, use Hogwarts metaphors, tone instructions

- Emphasizes precision, correctness, and thoroughness

## 11. Interview Talking Points

### How would you scale this?

- **Current bottleneck:** Single Ollama instance serializes requests
- **Scale solution:** Deploy multiple Ollama instances behind a load balancer, or use vLLM/TGI for batched inference
- **Architecture:** Stateless agents → horizontal scaling is trivial
- **Database:** PostgreSQL for persistence, Qdrant for vector search (Phase 3)

### Why not use CrewAI or AutoGen?

- **LangGraph is more flexible:** CrewAI/AutoGen are opinionated frameworks for specific agent patterns. LangGraph is a lower-level graph library that lets us define arbitrary orchestration patterns.
- **No LLM vendor lock-in:** LangGraph works with any LLM API, not just OpenAI.
- **Lightweight:** No heavy abstractions — just state, nodes, and edges.

### How do you handle errors?

- **FastAPI unreachable:** Rust falls back to hardcoded responses
- **Ollama timeout:** httpx 300s timeout → FastAPI 500 → Rust falls back
- **Empty question:** FastAPI 400 validation
- **Malformed response:** LangGraph state validation catches missing fields

### How would you add a new agent?

1. Create `agents/new_character.py` with `MEMBER` dict and `async def node(question)`
2. Create `prompts/new_character.txt` with system prompt
3. In `agents/planner.py`, import the new module and add:
   - A new node function
   - A `Send(new_character, state)` entry in the router
   - The node to the graph builder

### How does this compare to a simpler approach?

- **Naive approach:** Call Ollama 4 times sequentially in a FastAPI route handler
- **Problem:** No state management, no parallelism, no extensibility
- **Our approach:** LangGraph provides state management (reducers), parallel execution (Send), and a graph structure that maps naturally to future features (RAG nodes, memory nodes, tool-calling nodes)
